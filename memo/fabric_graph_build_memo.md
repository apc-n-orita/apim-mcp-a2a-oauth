# 机上メモ: Fabric グラフの作成 (PDF から知識グラフを作る)

状態: 机上検討のみ。何も作成・実行していない。確認できていない点は「未確認」と明記する。
目的: 資料 (PDF) から関連性のグラフを作り、Fabric Data Agent のデータソースとして使う。
検索インデックス (詳細) と合わせて、`foundryiq-acl-mcp` から引く構想の一部 (関連: `fabric_data_agent_kb_memo.md`)。

## 1. 全体像

| 段階                    | 手段                                                                         | 備考                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 1. PDF の取り込み       | ストレージアカウントへの OneLake shortcut を Lakehouse の `Files` に作る     | コピーせずに参照できる                                                                 |
| 2. ノードとエッジの抽出 | Notebook (PySpark / Python) で、PDF のテキスト抽出と LLM の呼び出しを行う    | パイプラインのアクティビティ単体では行えず、コードで書く                               |
| 3. テーブルの作成       | 同じ Notebook で、ノード用とエッジ用の Delta テーブルを `Tables` に書く      | Delta が Lakehouse の標準形式                                                          |
| 4. グラフの作成         | グラフモデルで、ノードの種類・エッジの種類・列のマッピングを定義して保存する | 保存すると取り込みが走る                                                               |
| 5. 全体の順序制御       | パイプラインから Notebook を実行し、その後にグラフを更新する                 | Lakehouse では、パイプラインで取り込みと変換をオーケストレーション・スケジュールできる |

パイプラインは流れの管理役で、抽出そのものは Notebook に書く。

## 2. 各段階の詳細 (Learn で確認した範囲)

### 2.1 shortcut (PDF の参照)

- 外部ソースとして Azure Blob Storage / ADLS Gen2 が使える。ADLS は DFS エンドポイント (`https://<アカウント名>.dfs.core.windows.net`) を指す。
- 認証は shortcut の作成者が指定する資格情報で行う。選べるのは、組織アカウント、アカウントキー、SAS、サービスプリンシパル、Workspace Identity。
- アカウントキーはストレージ全体の権限になるので避ける。Workspace Identity か、Storage Blob Data Reader を持つサービスプリンシパルが無難。
- ストレージにファイアウォールがある場合は、trusted workspace access の設定が必要。

### 2.2 Notebook での抽出 (未確認が多い)

- LLM の呼び出し先 (Foundry のモデルデプロイを呼ぶ形が自然) と、Notebook からの認証方法の公式手順は未確認。
- 出力は、ノード用とエッジ用の決まった列に揃える。構造化出力 (JSON スキーマ指定) を使うのが安全。
- 長い PDF は、ページや章で分割してから LLM に渡す。画像だけのページは、テキスト抽出で取れない。
- 再実行すると同じノードが重複するので、上書きにするか更新にするかを決める (2.2.1 を参照)。

#### 2.2.1 再実行の扱い: 全件の上書き / 増分 (更新分だけ処理)

増分の設計は一般的な Delta の使い方に基づく案で、Learn では書かれていない。

全件の上書き:

- 毎回、全 PDF を処理して、`nodes` / `edges` を作り直す。
- 実装が簡単で、重複や古いエッジの問題が起きない。
- 資料が少なく、実行がまれなら、こちらでよい。

増分 (新規・変更のあったファイルだけ処理):

1. 処理済みの管理表 (例: `processed_files`) を Delta テーブルで持つ。ファイルのパスと、最終更新時刻 (またはハッシュ) を記録する。
2. Notebook の開始時に、shortcut 先のファイル一覧と管理表を比べ、新規または変更のあったファイルだけを処理対象にする。
3. 対象の PDF だけを LLM に渡し、ノードとエッジを抽出する。
4. Delta の MERGE で反映する。
   - `nodes`: `id` をキーに MERGE (あれば更新、なければ追加)。
   - `edges`: `from_id` / `to_id` / `relation` の組をキーに MERGE するか、変更のあったファイルの出典 (`source`) の行をいったん削除して入れ直す。後者が簡単。
5. 管理表を更新する。

増分にするときの注意:

| 点                               | 内容                                                                                                                                           |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| ファイルの変更                   | 古い版のエッジが残らないよう、そのファイル由来のエッジを先に削除してから入れ直す (`source` 列が必要)                                           |
| ファイルの削除                   | 削除されたファイル由来のエッジと、他のどこからも参照されなくなったノードを、消すかどうかを決める                                               |
| 同じノードが複数のファイルに出る | `source` を 1 つの値にすると後勝ちで上書きされる。出典を配列で持つか、出典用のテーブルを分ける                                                 |
| ID の一貫性                      | 追加分の抽出時に、既存の `nodes` の ID 一覧を LLM に渡して、その中から選ばせると、表記ゆれによる重複を減らせる (4 章の対策と同じ)              |
| ファイルをまたぐ関連             | 1 つのファイルだけを見て抽出すると、別のファイルの概念との関連は出てこない。新しいノードと既存のノードの関連を探す処理を、別に入れる必要がある |
| 信頼度                           | 追加分と既存分で付け方がずれないよう、同じプロンプトとモデルを使う                                                                             |

グラフ側:

- Learn には、グラフモデルを保存すると Lakehouse のテーブルからデータが取り込まれて、読み取り用のグラフが構築されると書かれている。構造 (種類やプロパティ) の変更は、増分ではなく全データの再取り込みになる。
- データだけが増えた場合に、グラフの更新が増分か全件かは未確認。全件の再取り込みなら、テーブルを増分にしても、グラフの更新のコスト (容量の消費) は減らない。個人用途の規模なら問題にならない可能性が高いが、実測が必要。

判断: 資料が少なく Notebook の実行がまれなら、全件の上書きのほうがずっと簡単。増分にする価値が出るのは、資料の数や LLM の呼び出しコストが大きくなってから。

### 2.3 グラフモデル

- ノードの種類 (node type) は、ラベル、元になるテーブル、一意に識別する **key 列**、プロパティで構成される。テーブルの 1 行が 1 ノード。
- エッジの種類 (edge type) は、ラベル、元になるテーブル、**始点 (Origin) のノードとそのキー列**、**終点 (Target) のノードとそのキー列**で構成される。テーブルの 1 行が 1 本のエッジ。
- 1 列で一意にならない場合は、複合キーを使える。エッジ側でも、対応する複合キーの列を選ぶ。
- プロパティは自動では付かない。エッジにも、関係そのものを表す列 (信頼度など) を、必要なら自分でプロパティとして追加する。
- 保存すると、モデルの保存とデータの取り込みが 1 つの操作で行われる。Lakehouse が更新されたら、グラフも更新する必要がある (Schedule で定期更新できる。共有ワークスペースが前提で、My Workspace では使えない)。
- REST API だけで作ったグラフモデルは、Fabric ポータルのエディタで一度開くまで問い合わせできない。完全な自動化には、初回だけ手作業が必要。
- スキーマの変更 (ノード・エッジの種類やプロパティの追加・削除) は、増分では反映されない。保存して全データを再取り込みする必要がある。容量を消費するので、スキーマは最初に固めておく。

## 3. テーブル設計 (案)

今のローカルのグラフ (`graph.json`) が持っている情報を、列として残す。スキル側の「信頼度を必ず示す」方針を、そのまま維持するため。

ノード用テーブル (例: `nodes`):

| 列            | 内容                            |
| ------------- | ------------------------------- |
| `id`          | key 列。一意で、正規化済みの ID |
| `label`       | 表示名                          |
| `type`        | 概念の種類                      |
| `source`      | 出典 (ファイル名など)           |
| `source_page` | 出典のページ                    |

エッジ用テーブル (例: `edges`):

| 列                 | 内容                                               |
| ------------------ | -------------------------------------------------- |
| `from_id`          | 始点のノード ID (ノードの `id` と同じ形式・同じ型) |
| `to_id`            | 終点のノード ID (同上)                             |
| `relation`         | 関係の種類                                         |
| `confidence_label` | 抽出の確かさの区分 (明記 / 推定 / 曖昧 など)       |
| `confidence_score` | 信頼度の数値                                       |
| `source`           | 出典                                               |

- 列名と区分の値は案。最初に固めておく (スキーマ変更は全再取り込みになるため)。
- 同じ関係でも、種類ごとにエッジのテーブルを分けるか、`relation` 列で区別するかは、グラフモデルの作り方 (エッジの種類をいくつ作るか) とあわせて決める。

## 4. ノード ID とエッジの始点・終点の一致

Fabric のグラフは、エッジのテーブルの始点・終点の列の値が、ノードのテーブルの key 列の値と**一致するか**で、線を引く。一致しない行は、どのノードにもつながらず、グラフに現れない。

例: ノードに `node_a` があるのに、エッジが `Node_A` (大文字) を指す、またはノードにない値を指すと、つながらない。

Learn に書かれていること:

- キー列と、エッジのマッピングに使う外部キー列の**型を揃える**。型が違うとエッジ作成に失敗する。
- エッジが作られない場合は、始点・終点のマッピング列が、ノードのキー値と型の両方で一致するかを確認する。
- ノードのキーが一意でないと、ノードが重複する。

LLM で抽出するときに起きやすい理由: 同じ概念が、大文字小文字、全角半角、略称、言語の違いなどで、別の表記で出てくる。

対策 (Notebook に入れておく):

1. すべての ID を、同じ規則で正規化する (小文字化、空白の除去、全角半角の統一)。
2. ノードの表を先に確定する。エッジの抽出では、既存の ID 一覧を LLM に渡し、その中から始点・終点を選ばせる。
3. 書き出す前に、エッジの `from_id` / `to_id` が、すべてノードの `id` に存在するかを検証する。存在しない行は、ログに出して除外するか、ノードを追加する。
4. ノードの `id` に重複がないかを確認する。

ローカルのグラフ (`graph.json`) をそのまま移す場合は、すでにノード ID とエッジの始点・終点が対応しているので、この問題は起きにくい。新しく抽出する部分で気をつける。

## 5. アクセス制御 (テーブル単位のロール)

方針: 知識グラフなので、OneLake security のロールを**テーブルのスコープだけ**で付ける。行レベル (RLS) と列レベル (CLS) は使わない。

Learn で確認した範囲:

- OneLake security は、Lakehouse に付けるロールで、データへのアクセスを制御する。ロールは、権限 (Read / ReadWrite)、対象データ、メンバー (Entra のユーザー・グループなど) で構成される。
- ロールの対象データには、テーブル、フォルダ、スキーマを指定できる。Delta テーブルは、OneLake 上ではフォルダとして表されるので、フォルダと同じ方法で保護できる。
- RLS と CLS は、ロールの中でテーブルごとに足す任意の制限。足さなければ、テーブル単位の付与だけになる。
- ロールは付与のモデルで、拒否のロールはない。複数のロールに入っているユーザーは、権限が合算される。
- ReadWrite のロールには、RLS と CLS を含められない。
- Learn の「Read data secured with OneLake security」の表では、Graph in Fabric は RLS/CLS のフィルタリングに対応 (GA) と書かれている。

ロールの作り方 (案):

1. Lakehouse の「Manage OneLake security」で、ロールを作る。
2. 権限は Read、対象データはテーブル (`nodes`、`edges` など)、メンバーは Entra のユーザーかグループにする。
3. RLS と CLS は設定しない。

使うときの要点:

| 点 | 内容 |
|---|---|
| `DefaultReader` ロール | 既定で、ReadAll 権限を持つユーザーに、Lakehouse 全体の読み取りを許可する。テーブルごとに絞るなら、削除か編集が必要 |
| ワークスペースの役割 | Admin、Member、Contributor は、この制御の対象外。制限が効くのは、Viewer と、OneLake security のロールでアクセスを付与されたユーザー。利用者は Viewer にするか、アイテムの共有で渡す |
| グラフの利用権限 | グラフのアクセスは、そのグラフを持つワークスペースの中に限られる (ワークスペース外のユーザーは使えない)。共有を使うなら、グラフのアイテムを共有する |
| Data agent の前提 | Data agent を呼ぶユーザーは、Data agent と元データへの読み取り権限が必要 |

Foundry IQ のヘッダーとのつながり (`fabric_data_agent_kb_memo.md` を参照):

```
ユーザートークン (search.azure.com) → x-ms-query-source-authorization
  → AI Search の検索エンジンが OBO で Fabric 用トークンに交換
  → Data agent を、そのユーザーとして呼ぶ
  → Data agent がグラフを問い合わせる
  → OneLake security が、そのユーザーの権限でフィルタ
```

個々の記述は確認できているが、この経路を通しで確認したドキュメントは見つかっていない。

知識グラフ特有の気になる点 (未確認):

- テーブル単位の権限 (オブジェクトレベルのセキュリティ) が、グラフの問い合わせでどう効くか。Learn の表は RLS/CLS への対応を示しているが、テーブル単位の個別の記述は見つかっていない。
- エッジのテーブルは読めるのに、端点のノードのテーブルが読めないユーザーがいるとき、そのエッジがどう扱われるか (見える、消える、エラー)。
- グラフは、保存したユーザーが構築した読み取り用のスナップショット。他のユーザーが問い合わせるときに、テーブルの権限が再評価されるか。

安全に始める設計案:

- アクセスの区分ごとに、グラフを分ける (例: 全員向けと限定向けを、別の Lakehouse かテーブルの組で作る)。グラフのアイテム共有と、テーブルのロールを併用すれば、端点が見えないエッジの問題を避けられる。
- テーブルを区分ごとに分ける場合、エッジのテーブルの区分は、端点の 2 つのうち、より厳しいほうに合わせる。
- まず、テスト用のユーザー (Viewer) で、テーブルのロールが、グラフの問い合わせに効くかを確かめる。
